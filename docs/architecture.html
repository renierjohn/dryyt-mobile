Dryyt — Architecture, Workflows, Tables

Cloudflare Worker (worker/, Hono) + D1 + Durable Objects + R2, Expo app (src/). Money is integer centavos (5000 = ₱50.00).

System overview

Every protocol in the system and where it goes.

HTTPS REST call (JWT bearer) WSS WebSocket message RPC Worker calls a Durable Object method (in-Cloudflare, not over the internet) ALARM DO timer PUSH phone notification: Worker → Expo Push → APNs/FCM; reaches the app even when closed R2 object storage Wtable write Rtable read

Throughout, screens also poll GET /dropoffs/:id (customer, owner) and GET /drivers/me (driver: online, busy, current job) — 5 s, or 30 s while a socket is live. The driver's online switch is also saved on the phone (secure store, per user) so it shows instantly on start; /drivers/me overrides it. On the customer screen any socket message other than drivers/loc/stale triggers an immediate refetch.
PUSH in the app (usePushNotifications(role), mounted by the customer, driver and owner tab layouts): registers the token (needs a dev/release build with google-services.json and the FCM V1 key in EAS; not Expo Go), shows pushes while the app is open too, refreshes the affected queries on arrival (['dropoff', id]; driver ['driver']; owner ['owner']; never /history), and on tap opens driver → Available tab, customer → /customer/dropoff/[id], owner → /owner/dropoff/[id]. Every push carries { transaction_id }. "New drop off nearby" uses Android channel new-dropoff and sound dryyt.wav (bundled via app.json expo-notifications.sounds), so it plays the Dryyt chime even with the app closed; every other push uses channel default and the system sound (PUSH_STYLES in worker/src/lib/push.ts). Notification icon: assets/images/notification-icon.png, tinted #208AEF. Drivers on a live dispatch socket get no "new drop off" push, so push and socket never double up.

WebSocket events

Ticket via POST /ws/ticket, then /ws/dispatch or /ws/trip/:room. Reconnect backoff 1 → 2 → 5 → 10 s. The dispatch socket closes while the app is in the background (so Dispatch pushes the driver instead) and reopens immediately on return; trip sockets stay open. Drivers resend their latest location on every (re)connect, so requests / the customer's map don't wait for the next GPS fix.

Distance priority

There is no automatic assignment. Distance decides who sees the request and in what order; the first eligible driver to tap Accept wins.

Edge cases & races

CaseHandling
Customer cancels while a driver's accept is in flightBoth are guarded on status. If cancel lands first, accept's UPDATE matches 0 rows → taken. If accept lands first, the cancel batch frees that driver and they get cancelled.
Accept lands in D1 but the DO restarts before savingOn the next alarm, Dispatch re-reads D1, rebuilds the hold and still runs the 60 s confirm timeout.
Search expires at the same moment as an acceptExpire is UPDATE … WHERE status='searching'; whichever lands first wins, the other sees 0 rows and re-reads D1.
Customer already has an active drop offUnique index transactions_one_active_per_customer rejects a second one.
Shop blocks a driver mid-searchThe block list is captured at create / requeue, so it applies from the next requeue or request.
Driver app closed or in the background when a request appearsPUSH "New drop off nearby" with the Dryyt chime (backgrounding closes the dispatch socket, so the driver counts as idle). Tapping it opens the Available tab, which reconnects to Dispatch; they accept from the list. Requeues (reject, confirm timeout) don't push again.
Routing slow or down at createOSRM (5 s) → OpenRouteService (5 s, needs ORS_API_KEY) → straight line × 1.3. Each fallback logs a warning; the drop off always books. The transaction doesn't record which source priced it.
Two accounts signed in on one phone (one after the other)The newer sign-in takes the token (POST /me/push-token clears it from the other account), and sign out clears it, so one user's pushes never ring for another.
Phone can't get a push tokenApp reports [push-token] failed {step, error} to the worker log and retries on every return to the foreground. getExpoPushTokenAsync + SERVICE_NOT_AVAILABLE = Google Play services can't reach FCM (network blocking ports 5228–5230, outdated/restricted Play services, wrong clock, or no Play services); not an app bug.
Driver verified while a photo upload is in flightGuarded UPDATE … WHERE status = 0 matches 0 rows → new R2 object deleted, 409.
