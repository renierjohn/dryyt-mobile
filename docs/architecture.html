Dryyt — Architecture, Workflows, Tables

Cloudflare Worker (worker/, Hono) + D1 + Durable Objects + R2, Expo app (src/). Money is integer centavos (5000 = ₱50.00).

System overview

Every protocol in the system and where it goes.

HTTPS REST call (JWT bearer) WSS WebSocket message RPC Worker calls a Durable Object method (in-Cloudflare, not over the internet) ALARM DO timer PUSH phone notification: Worker → Expo Push → APNs/FCM; reaches the app even when closed R2 object storage Wtable write Rtable read

Workflow: Pickup WSS PUSH

Feature switch: PICKUP_ENABLED in worker/wrangler.jsonc and src/constants/features.ts, both on. Off → every /orders, /jobs and /menu route returns 403 "Pickup is not available yet", /history lists drop offs only, and the app hides the Pickup card and screens (Stack.Protected) and never fetches useOrder / useAvailableJobs / useActiveJob. Turn both on or off together. The tests run with Pickup on (vitest.shared.ts), plus pickup-off.test.ts for the switch.

Store → customer (food/beverages or laundry). Food is paid upfront to the store's payment QR and confirmed by the owner before drivers see it; laundry is cash on delivery. Delivery fee: road distance × the store group's rate for a pinned spot (split into the driver's share and service_fee), or the flat DELIVERY_FEE for a typed address. Live through two DOs in do/pickups.ts: PickupBoard ("all", the job board) and OrderRoom ("order-<id>", from Send proof of payment until delivered or cancelled; also runs the Done Pay reminder and auto-accept alarms); every route tells them after D1 commits (pickupChanged in lib/pickup-live.ts). Tables orders, order_items. Routes in orders.ts, jobs.ts, owner.ts.

WebSocket events

Ticket via POST /ws/ticket, then /ws/dispatch, /ws/trip/:room, /ws/pickups or /ws/order/:id. Reconnect backoff 1 → 2 → 5 → 10 s. The dispatch and pickups sockets close while the app is in the background (so Dispatch pushes the driver instead) and reopen immediately on return; trip and order sockets stay open. Drivers resend their latest location on every (re)connect, so requests / the customer's map don't wait for the next GPS fix.

Distance priority

There is no automatic assignment. Distance decides who sees the request and in what order; the first eligible driver to tap Accept wins.

RuleWhereDetail
Candidate searchDispatch.nearbyDriversGeohash precision-5 cells (~5 km), 11×11 cells around the customer, then exact haversine ≤ 20 km. Result sorted nearest first.
EligibilitynearbyDrivers, driversFor, requestsForSocket connected to Dispatch, location < 30 s old, not holding another request, not in the shop's driver_blocks, not in a reject cooldown for this customer, driver's vehicle = the request's vehicle_type (Dispatch.excluded; no vehicle set counts as motorcycle). Verified + online toggle + not busy is enforced when connecting / accepting.
Driver's list orderrequestsForAll searching requests within 20 km, sorted by distance_km ascending, each tagged green/amber.
Customer's viewdriversForPositions + colour only (no names) for eligible drivers within 20 km.
Accept guardDispatch.acceptRejected as taken if the driver is > 20 km away, blocked or cooling down, or the request isn't searching; error if the driver has no location yet.
App closedpushIdleDriversVerified, online, not-busy drivers with the request's vehicle, a push token and no socket get a push if their last D1 location is ≤ 20 km away, or unknown.
FeecomputeFeesUses road km customer → shop (OSRM → OpenRouteService → straight line × 1.3) and the rate of the vehicle the customer chose, not the driver's distance. Every driver (all with that vehicle) sees the same fee for a request.

Multiple drivers available

Several drivers see the same request. D1 decides the race with guarded UPDATE … WHERE status = 'searching'.

SituationResult
Two drivers tap Accept togetherFirst guarded UPDATE wins → accepted. Loser's busy is reset → taken ("Another driver took that one.").
Driver already on a job tries to acceptUPDATE drivers SET busy=1 WHERE busy=0 changes 0 rows → error "Finish your active job first". One job per driver across Pickup and Drop off.
Many requests near one driverDriver sees all of them, nearest first; can only hold one.

Pickup scenarios

What happens in each branch of the Pickup flow. Pickup's only alarms are on a food order waiting for Done Pay (owner reminder every 1 min ×10, auto-accept at 11 min); every other state waits until someone acts. Every status change is a guarded UPDATE … WHERE status = …, so a race leaves exactly one winner and the loser gets a 409.
