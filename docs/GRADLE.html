Gradle builds

What happens between bun run gradle:preview and an installable APK on Windows: which tools run, in what order, and why no container or virtual machine is needed. Versions to install are in build-tools.md.

Overview

The Android app is a normal Android Gradle project in android/, generated by bunx expo prebuild. Gradle drives every step: it bundles the JavaScript, compiles Kotlin/Java and C++, shrinks the code, and packs and signs the APK. Every tool it calls is a native Windows program.

ScriptGradle taskAPI (EXPO_PUBLIC_API_URL)Output
bun run gradle:devassembleDebugfrom .env (Metro serves the JS)debug APK
bun run gradle:previewassembleReleasehttps://app-preview.dryyt.comrelease APK
bun run gradle:releasebundleReleasehttps://dryyt.comAAB for Google Play

All three go through scripts/gradle.ts, which sets the API URL, gives the Gradle daemon the memory EAS uses (GRADLE_OPTS with -Xmx4g -XX:MaxMetaspaceSize=1g), turns on the Gradle build cache (--build-cache), and runs gradlew.bat through cmd on Windows (./gradlew on macOS).

Container or VM?

Not needed Gradle builds directly on Windows. The JDK, Android SDK, NDK, CMake and Node all ship Windows binaries, and Gradle runs them as ordinary processes. No Docker, WSL or VM is involved, and no emulator either: an emulator or phone is only needed to run the APK, not to build it.

EAS builds on a Linux VM (Ubuntu, /home/expo/... in the build log) only because it is a shared cloud service that has to isolate each build. The toolchain inside is the same: JDK 17, Gradle 9.3.1, NDK 27.1.12297006, CMake 3.22.1. A local build matches EAS by installing the same versions, not by copying its VM.

How Gradle compiles

bun run gradle:preview └─ scripts/gradle.ts → cmd /c gradlew.bat assembleRelease (EXPO_PUBLIC_API_URL, GRADLE_OPTS set) └─ Gradle wrapper → Gradle 9.3.1 daemon on the JDK in JAVA_HOME, 4 GB heap ├─ 1. Settings autolinking finds native modules in node_modules ├─ 2. Configuration every module's build.gradle; SDK 36, NDK, Kotlin versions set └─ 3. Execution ├─ JS bundle Node + Metro → index.android.bundle → hermesc → Hermes bytecode ├─ Codegen Node → C++/Java glue for new-architecture modules ├─ Resources manifest merge, AAPT2 compiles and links res/ ├─ Kotlin/Java kotlinc + javac → .class files ├─ C++ CMake + Ninja + NDK clang → .so for 4 CPU types ├─ R8 / D8 shrink, minify, convert to classes.dex └─ Package zip → zipalign → apksigner → app-release.apk
  1. Wrapper and daemongradlew.bat downloads Gradle 9.3.1 once into %USERPROFILE%\.gradle\wrapper and starts a background daemon on the JDK in JAVA_HOME. The daemon's memory comes from org.gradle.jvmargs: 2 GB in android\gradle.properties, raised to 4 GB by scripts/gradle.ts. Later builds reuse a daemon only if its settings match; gradlew --stop kills it (do that after changing JAVA_HOME, ANDROID_NDK_HOME or the memory setting).
  2. Settings: autolinkingsettings.gradle applies Expo's autolinking, which reads node_modules and adds every package with Android code (expo-updates, react-native-reanimated, Firebase, Google Sign-In, ...) as its own Gradle module.
  3. ConfigurationGradle evaluates every module's build.gradle. Expo's root project plugin sets shared versions: compileSdk/targetSdk 36, minSdk 24, build-tools 36.0.0, Kotlin 2.1.20, and NDK 27.1.12297006 from React Native. Most build failures that happen in seconds (like the broken-NDK error) happen here.
  4. JavaScript bundleThe React Native Gradle plugin runs Node with Metro to bundle the app's JS into index.android.bundle, with EXPO_PUBLIC_API_URL baked in. The Hermes compiler (hermesc, shipped with React Native) turns it into bytecode so the app starts fast. Debug builds skip this and load JS from Metro instead.
  5. CodegenFor the new architecture, Node generates C++ and Java glue code from the TypeScript specs of native modules.
  6. Resources and manifestAll modules' AndroidManifest.xml files are merged into one, and AAPT2 (from build-tools) compiles icons, layouts and strings and generates the R classes.
  7. Kotlin and JavaThe Kotlin compiler and javac from the JDK compile each module to .class files. This step and the C++ step take most of a clean build's time.
  8. C++ (native libraries)Modules with C++ (React Native, Reanimated, Worklets, expo-updates, Nitro, ...) are built with CMake 3.22.1 and Ninja, which call the NDK's clang. Each one is compiled four times, once per CPU type: arm64-v8a, armeabi-v7a, x86, x86_64. The results are .so files.
  9. Shrink and dexFor release builds, R8 (inside the Gradle daemon, so it is the step that needs the 4 GB heap) removes unused classes and resources and minifies names (enableMinifyInReleaseBuilds, enableShrinkResourcesInReleaseBuilds in app.config.js), then converts the bytecode to Android's classes.dex.
  10. Package and signDex files, .so files, resources and the JS bundle are zipped into the APK, aligned with zipalign and signed with apksigner. A prebuilt project signs release builds with android/app/debug.keystore, so Google and Facebook sign-in need that key's SHA-1 registered (see App build). bundleRelease packs an AAB instead, which Google Play signs.

Re-running after a failure

Gradle does not start over after a failed build. Tasks that finished are skipped on the next run (UP-TO-DATE) as long as their inputs did not change, so the build resumes at the task that failed. The JS bundle re-runs when switching between gradle:preview and gradle:release, because the API URL is one of its inputs.

On top of that, scripts/gradle.ts passes --build-cache: task outputs are stored in %USERPROFILE%\.gradle\caches\build-cache-1 and reused (FROM-CACHE) even after gradlew clean, prebuild --clean or switching targets. The first build fills the cache, so only later builds get faster.

ActionEffect on the next build
Re-run after a failureFast resumes at the failed task
gradlew clean, bunx expo prebuild --cleanCache outputs come back from the build cache where inputs match
Deleting .cxx foldersSlow C++ is reconfigured and recompiled
Deleting %USERPROFILE%\.gradle\cachesSlow everything is downloaded and built again
The configuration cache (--configuration-cache) is left off: React Native and Expo Gradle plugins do not fully support it.

What the cache holds

Everything under %USERPROFILE%\.gradle\ (~/.gradle/ on macOS):

FolderHoldsFilled bySafe to delete?
wrapper\dists\Gradle itself (9.3.1)gradlew.bat on first runYes, re-downloaded (~200 MB)
caches\modules-2\Downloaded libraries: Kotlin, AndroidX, Firebase, Play services, React Native and Hermes AARsThe first buildYes, but the next build downloads everything again (needs internet)
caches\transforms-*\Libraries unpacked and converted for Android (AARs extracted, desugared, dexed)Every buildYes, rebuilt from modules-2
caches\jars-*\, caches\9.3.1\Compiled build scripts and Gradle's plugin classesGradle startupYes
caches\build-cache-1\The build cache: outputs of single tasks (compiled .class files, compiled resources, .dex files, merged manifests), each stored under a fingerprint of the task's inputsEvery bun run gradle:* (--build-cache)Yes, slower until it fills again
daemon\Gradle daemon logsEach daemonYes

Before a task runs, Gradle fingerprints its inputs (source files, settings, library versions). If build-cache-1 has an output for that fingerprint, Gradle copies it in and the task shows FROM-CACHE; otherwise the task runs and its output is saved.

Outside .gradleRole
android\app\build\, node_modules\*\android\build\The last build's outputs; why a re-run after a failure skips finished tasks (UP-TO-DATE)
android\app\.cxx\, node_modules\*\android\.cxx\CMake's working files for C++. Not in the build cache, so deleting them recompiles all C++
%LOCALAPPDATA%\Android\Sdk\Installed SDK packages (NDK, CMake, build-tools); not a cache
Gradle removes cache entries unused for about a week, but caches\ often reaches 5–15 GB with React Native. When disk is tight, delete build-cache-1\ and transforms-*\: that frees the most without a full re-download.

Outputs

gradle:dev android\app\build\outputs\apk\debug\app-debug.apk gradle:preview android\app\build\outputs\apk\release\app-release.apk gradle:release android\app\build\outputs\bundle\release\app-release.aab

Install an APK on a USB-connected phone with adb install -r <path>. The AAB is only for Google Play.
