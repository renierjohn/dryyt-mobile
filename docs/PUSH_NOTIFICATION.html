Push notifications

How the worker sends pushes and confirms they were delivered, the limits, and how to set up EXPO_ACCESS_TOKEN. Updated 2026-10-19.

Summary

  • Pushes go through Expo's push service (exp.host), which passes them on to FCM (Android) and APNs (iOS).
  • Before this update the worker sent pushes and never read Expo's reply, so it couldn't tell whether they went through.
  • Now the worker reads each ticket (Expo's immediate per-message answer), retries when Expo is busy or down, and saves accepted tickets.
  • A cron job runs every 15 minutes and fetches each ticket's receipt, which says whether FCM/APNs accepted the push. When a phone is reported as no longer registered, its token is cleared.
  • When the EXPO_ACCESS_TOKEN secret is set, every request to Expo includes it, so Enhanced Security for Push Notifications can be turned on.
  • Sending stays best effort: a push failure never fails the API request or Durable Object action that triggered it.

UsersNo limitOne push_token per user. The most recent phone to register is the one that gets pushes.

Only "New drop off nearby" (do/dispatch.ts) goes to many users. Every other push goes to one user.

Reliability: what's still out of our control

  • Android battery savers (Xiaomi, Oppo, Vivo, Huawei) can delay or drop notifications.
  • iOS Focus/Do Not Disturb, and users who deny notification permission.
  • Push only wakes the app up. The live dispatch socket and polling remain the source of truth. Drivers connected to the socket don't get the "new drop off" push at all.

EXPO_ACCESS_TOKEN

Without it, anyone who has a user's ExponentPushToken[…] can send that phone a notification that looks like it came from Dryyt. With Enhanced Security for Push Notifications turned on, Expo rejects any push that doesn't carry your access token. It has no effect on speed or delivery. It's optional: when the secret isn't set, the worker sends exactly as before.

  1. Signed in to expo.dev, open expo.dev/settings/access-tokens and click Create token. If the project belongs to an organization, switch to it, open Settings → Access tokens, and preferably create a robot user token there.
  2. Copy the token. It's shown only once.
  3. From worker/: 
    bunx wrangler secret put EXPO_ACCESS_TOKEN
bun run db:migrate:remote
bun run deploy
  4. After the deploy, enable Enhanced Security for Push Notifications in the Expo project's settings.
Order matters. Turning on enhanced security before the deployed worker sends the token makes Expo reject every push, which shows up in the logs as [push] rejected with status 401. Run the migration before deploying, too. Until the push_tickets table exists, saving tickets fails, and the error is only logged.

Log lines to watch

LogMeaning
[push] retryableExpo returned 429/5xx or the network failed. The request will be retried.
[push] gave upStill failing after 2 retries. That batch was not sent.
[push] rejectedExpo returned another 4xx error, such as 401 from a bad or missing access token.
[push] delivery errorA ticket or receipt error other than an unregistered phone, such as MessageTooBig or InvalidCredentials (FCM/APNs keys).
